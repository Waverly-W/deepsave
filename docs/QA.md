DeepSave Pro - 产品规格说明书 & 决策问答记录 (Q&A Specs)文档信息内容关联项目DeepSave Pro (SecondBrain-Hybrid)版本v1.0 (Decision Freeze)决策人Product Manager & System Architect状态已锁定 (Locked)一、目标与边界 (Goals & Boundaries)1. 用户模式与权限决策：个人单用户 (Single User)。理由：NAS 场景通常是个人私有设备。引入多租户/权限隔离会显著增加鉴权逻辑复杂度，MVP 阶段不涉及。实现：单一管理员账号（Admin），通过 Basic Auth 或简单 Token 验证。2. MVP 最小闭环 (Scope)Must Have (必须有)：URL 采集（支持剪贴板监听、Chrome 扩展）。文本处理流（爬虫 -> 摘要 -> 标签）。混合搜索（关键词 + 向量）。Web 端 Chat/Gallery 双视图。Postponed (延后 Phase 2)：PDF/Office 文档解析。移动端独立 App（暂时用 PWA/Telegram Bot 代替）。复杂的知识图谱可视化。Won't Do (不做)：多人协作编辑。SaaS 化部署。3. 核心成功指标 (KPI)处理成功率：> 95% 的 URL 能成功提取正文（排除死链）。响应时延：API 模式下，从输入 URL 到生成卡片 < 15秒。召回准确率：Top 10 搜索结果中，用户点击率 > 40%。5. 语言支持内容语言：多语言混合（UTF-8），后端需支持中/英/日文的分词与 Embedding。UI 语言：MVP 仅支持 简体中文，架构预留 i18n key。二、目标用户与使用场景 (Target Audience)6. 人群优先级P0: 效率派 (Efficiency User) -> 追求“混合架构”带来的速度与隐私平衡。P1: 隐私极客 -> 需确保断网能跑（本地模型）。P2: 开发者 -> 提供 API 即可。7. 数据量级预期日均：~20-50 条。峰值：批量导入时约 1000 条/次。并发限制：限制为 3 个并发抓取任务（保护 NAS IO）。9. 最低硬件基线 (Low-end Baseline)CPU: Intel Celeron J4125 (4核 2.0GHz) 或同级 AMD。RAM: 8GB (Docker 运行 Next.js + Python + DB + Chroma 至少需要 4-6GB)。注意：若内存 < 8GB，强制禁用本地 LLM，仅允许 API 模式。三、采集渠道 (Ingestion)10. 剪贴板监听OS 支持：Windows, macOS。实现：不作为核心应用内置，而是提供一个轻量级 Python/Go 脚本或使用 uTools/Raycast 插件调用 API。MVP 不开发原生 Desktop Daemon，以降低开发成本。11. 菜单栏/托盘交互决策：MVP 暂不做独立托盘程序。利用浏览器扩展图标显示状态。13. 浏览器扩展决策：必须进入 MVP。支持：Chrome (Manifest V3)，可兼容 Edge/Brave。Firefox 延后。14. 批量导入决策：延后至 Phase 2。MVP 仅支持单条或粘贴板多行 URL。15. 内容类型优先级P0: 网页文章 (Article)。P1: 网页图片 (Image URL)。P2: 纯文本笔记 (Memo)。Postponed: PDF, 音频, 视频。16. Smart Scraper 判定规则规则：先尝试 HTTP GET (Trafilatura)。若 Content-Length < 1000 字符 OR <body> 包含 <div id="app"> (SPA 特征) -> 触发 Fallback。17. Playwright 兜底策略触发：HTTP 解析失败或内容过短。配置：Timeout = 30s。Retries = 1。资源：单实例运行（Singleton），处理完关闭 Context。18. Cookie/UA 配置MVP：使用通用 User-Agent 库。Phase 2：在 Web 设置页提供 Cookie 填写框（用于微信/付费墙网站）。19. 失败处理UI 显示红色“抓取失败”卡片。保留原始 URL，允许用户“重试”。五、 AI 路由与模型选择 (Routing & Models)20. Router 实现决策：启发式规则 (Heuristic Rules)。逻辑：URL 后缀 (.jpg, .png) -> Vision Agent。URL 域名 (github.com, stackoverflow.com) -> Tech Agent。其他 -> Editorial Agent。理由：简单可靠，无需模型开销。21. 覆写结果支持用户手动修改分类（UI 下拉菜单），修改后触发重新处理。22. 敏感内容定义：不做主动检测。NAS 是私有设备，内容合规责任在用户。23. 云端模型供应商决策：OpenAI Compatible API。兼容：只要兼容 OpenAI SDK 的服务商（DeepSeek, Moonshot, Azure）均可配置 Base URL 和 Key。24. 本地模型管理决策：不提供模型下载 UI。方式：用户需自行配置外部 Ollama 地址。DeepSave 只负责调用，不负责管理 Ollama 的模型文件。六、向量与检索 (Vector & Search)25. 向量库选型决策：ChromaDB。理由：Docker 部署简单，Python 生态最佳，无需复杂的 PostgreSQL 插件配置（pgvector 对小白用户配置有门槛）。26. BM25 实现决策：使用 PostgreSQL tsvector (Full Text Search) 代替标准 BM25。理由：减少技术栈复杂度。PG 的全文检索对于个人数据量级（< 10万条）足够高效。27. Rerank 策略决策：Reciprocal Rank Fusion (RRF) 算法。逻辑：Score = 1/(k + PG_Rank) + 1/(k + Vector_Rank)。无需额外的 Rerank 模型推理（节省 NAS 算力）。28. 向量策略维度：取决于 Embedding 模型（推荐 text-embedding-3-small 或 bge-m3）。分块：RecursiveCharacterTextSplitter, Chunk Size = 1000, Overlap = 200。更新：全量覆盖。重新处理文章时，删除旧向量，插入新向量。29. 排序因子默认：混合相关度。可配置：按时间倒序（最新）、按相关度。七、数据模型与存储 (Data & Storage)30. JSON Schema统一结构：{
  "meta": { "title": "...", "author": "...", "published_at": "..." },
  "analysis": { "summary": "...", "tags": [], "sentiment": "..." },
  "tech_stack": [] // 仅 Tech 类有
}
31. 文件资产路径：/data/artifacts/{uuid}/。加密：否。文件系统层面不加密，依赖 NAS 自身的全盘加密。32. 备份/导出支持“导出全部为 Markdown + 资源文件夹”。33. 审计日志仅保留 task_logs 表，记录任务耗时与状态，保留 7 天，用于排查性能问题。八、UI/UX 细节 (UI/UX)34. 深色模式决策：跟随系统，默认深色。不强制。35. Recall 算法逻辑：Random(1): 随机抽取一条 > 30天未访问的内容。History(1): 去年今日（如有）。刷新：每次刷新页面或每 24 小时。36. 卡片布局固定布局：左图右文（桌面）/ 上图下文（移动端）。隐藏项：Debug 信息（Token 消耗、处理耗时）默认隐藏，Hover 显示。37. Deep Reader 侧边栏默认：摘要 (Summary) Tab。38. 搜索框全局常驻：顶部导航栏中央。逻辑：单一输入框。系统自动判断是“命令”（如 /tag python）还是“自然语言搜索”。39. 每日回顾通知决策：Web 端 Toast/Modal 弹窗。不接入邮件/推送（配置太繁琐）。九、安全与配置 (Security)40. API Key 存储决策：本地 .env 文件（部署时注入）或 SQLite/PG 数据库（加密字段）。MVP：UI 设置页输入 -> 后端加密存入 DB。41. 多环境不需要。仅区分 DEV (Local) 和 PROD (Docker)。42. 访问控制边界：默认监听 0.0.0.0。Auth：NextAuth.js (Credentials Provider)，单一密码登录。43. 合规在“关于”页面增加免责声明：本工具仅供个人学习存档使用。十、部署与运维 (Deployment)44. 部署方式必须 Docker Compose。这是 NAS 用户的唯一通用标准。45. 服务清单 (Container List)deep-save-web (Next.js)deep-save-api (FastAPI + Celery Worker)postgresredischromadb(Ollama 可选，通常复用 NAS 上已有的)46. 观测性Docker Logs。不引入 Prometheus/Grafana（太重）。47. 重试策略Celery 配置：autoretry_for=(Exception,), retry_backoff=True, max_retries=3。十一、范围冲突与文档一致性 (Consistency)48. TECH_STACK 变更锁定：Next.js + Python FastAPI + PostgreSQL + ChromaDB。MVP 期间禁止变更。49. SQLite vs PG最终决定：PostgreSQL。理由：ChromaDB 和 Celery 在高并发下配合 PG 更稳定，且 NAS 用户习惯运行 PG 容器。50. UX 规范指导性：UX 文档为设计指导，非硬性约束。以 shadcn/ui 默认组件库能力为准，减少定制 CSS 工作量。十二、里程碑与交付 (Milestones)51. Phase 1 时间表W1: 框架搭建 (Docker Compose, Next.js init, FastAPI init)。W2: 核心采集 (Scraper) 与 数据库 (PG/Chroma) 连通。W3: AI 接入 (Hybrid Router) 与 后端处理流。W4: 前端对接 (Chat/List) 与 收尾测试。预计可用日期：T+30天。52. MVP 牺牲项牺牲移动端适配的完美度（依靠 Next.js 响应式，不做专门优化）。牺牲“知识图谱”的可视化展示。牺牲对复杂动态网页（如抖音/小红书）的抓取成功率。
